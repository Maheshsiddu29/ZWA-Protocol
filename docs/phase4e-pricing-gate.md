# Phase 4E-C pricing and proof-binding gate

Research checked on 2026-10-12 against current primary provider documentation and the local checkout source. This is a design finding, not a live price integration or purchase acceptance.

## Provider identity and data trust

- [Pyth Core feed documentation](https://docs.pyth.network/price-feeds/core/price-feeds) states that each pair has a unique feed ID and that Stable and Beta IDs differ. Its [feed-ID page](https://docs.pyth.network/price-feeds/core/price-feeds/price-feed-ids) is the authoritative lookup, but the accessible page text did not expose a full XAU/USD or ZEC/USD mapping in this review. The current `exchange.pricing` and website code contain a candidate full XAU/USD ID; it remains **unverified** and must not unlock executable quotes.
- Pyth's [Core upgrade instructions](https://docs.pyth.network/price-feeds/core/upgrade/preparing) say Hermes has required an API key since the August 26, 2026 upgrade. This workspace has no authorized key or fresh official metadata response. The existing HTTPS adapter therefore remains unavailable. Even with a key, HTTPS transport and provider identity would be trusted; the current app does not verify the signed update against a Pyth trust root.
- [Chainlink's data feed interface](https://docs.chain.link/data-feeds/api-reference) exposes `decimals`, `description`, `latestRoundData`, and `updatedAt`. Its [feed selection guidance](https://docs.chain.link/docs/selecting-data-feeds) calls for source-quality and stale-value controls. No exact XAU/USD or ZEC/USD Chainlink network contract was selected or authenticated for this pinned Zcash regtest. An EVM feed response cannot be called Zcash consensus-verified merely because a contract exists elsewhere.
- Pyth's [Solana push-feed list](https://docs.pyth.network/price-feeds/core/push-feeds/solana) confirms that a ZEC/USD feed is listed, but its displayed ID is abbreviated. No full ZEC/USD ID, units/exponent sample, timestamp, or authenticated live value was verified here. Native-ZEC conversion stays disabled.

## Local proof gap

The repository contains the frozen Phase 0 `TradeCommitmentV1` specification in `docs/trade-commitment-v1.md`, and a separate Phase 4C.1 native-ZEC V2 circuit/adapter in `checkout/authorization/`. A repository search found **no separately named `TradeCommitmentV2` schema** to amend. `checkout/quote.py` fixes the actual `QuoteV1` fields and digest; they include AssetBase, quantity, exact native ZEC amount, receivers, fee, sponsor outpoint, nonce, and height expiries. They do not contain a price-source ID, source observation time, source unit, USD conversion, spread, or wall-clock quote expiry.

`checkout/authorization/native_zec_v2.js` recomputes its native-ZEC trade commitment from AssetBase, buyer receiver, the current QuoteV1 digest, and transaction expiry height. The Groth16 verifier checks those public signals. Because the QuoteV1 digest does not include the price snapshot, a proof can validate the exact chosen ZEC payment **without proving how that payment was derived**. The three Phase 4E-A purchases exercise that exact-amount path with fixed operator test prices. They provide no oracle-derived execution evidence.

The safe next implementation is a separately versioned experimental trade/quote statement that canonically binds the provider identity, signed or transport-authenticated snapshot commitment, observation and quote times, units, conversion arithmetic, spread, fees, chain context, and exact QuoteV1 settlement digest. It needs its own reviewed proof circuit/verifier and golden vectors, plus coordinator checks immediately before authorization and submission. V1 and the frozen native-ZEC V2 circuit must not be silently reinterpreted. Until that path and a verified live provider are in place, `MARKET_REFERENCE` and issuer NAV remain indicative, and no oracle-derived asset may be marked buy-enabled.
