# Phase 3.5C: ZIP-236 coinbase fee accounting

## Result and stop rule

**REJECTED_WITH_CONSENSUS_REASON.** The sole positive-fee two-ZSA swap block was rejected by the pinned Zebra regtest with:

```text
Block { source: Commit(CloneError { source: CommitSemanticallyVerifiedError(
  UnshieldedTransparentCoinbaseSpend {
    outpoint: OutPoint {
      hash: transaction::Hash("52d16b3f37b8e0a2cc1cf889b5ac7f8be6de18aef724fd601afbef1d9843cf6e"),
      index: 0
    }
  }
) }) }) }
```

The candidate's coinbase contained **625,005,000 zatoshis**, exactly the 625,000,000-zatoshi subsidy plus the candidate's 5,000-zatoshi fee. This passed the earlier `InvalidMinerFees` stage, but it did not enter the chain. The new rejection is for spending a transparent coinbase output in a transaction that also has a transparent change output. No second positive-fee submission was made. The purchase, checkout API, wallet, receipt service, and frontend remain out of scope pending owner review.

## Starting state, pinned rules, and root cause

The product branch began clean at `integration/zwa-checkout-poc` / `11186f8e6926fb8af10c7a2b87592071b867a720`. The non-frozen tool branch `phase35b/txid-conversion` held `599be2f647ce19982c45eb18cbf52801f38fdac7`. Its original checkout had pre-existing edits and the quarantined `zcutil/fetch-params.sh` deletion; neither was modified or restored. Work was done in an isolated tx-tool worktree branched from `599be2f` as `phase35c/coinbase-fee-accounting`. The pinned Zebra source was clean at `0aef55cea41b83f17610e6ea708e59995f9e739f`; the disposable image ID was `sha256:540a3429ef14ff3c575258255e4310951606d16c86ec5e1c37e285ea95178185`. The swap stack's Orchard and librustzcash pins remained `d91aaf146364a06de1653e64f93b56fac5b3ca0f` and `5a55da948498dd0995d0f438b4c8e9a3f0150154`.

[ZIP 236](https://zips.z.cash/zip-0236) requires coinbase input and output value to balance exactly from NU6 onward. The pinned Zebra implementation in `zebra-consensus/src/block/check.rs::miner_fees_are_valid` compares `transparent outputs - Sapling value balance - Orchard value balance + deferred contribution` with `block subsidy + block miner fees`. It uses equality for every upgrade at or after NU6; there is no separate NU7 fee exception in this pinned check. `zebra-consensus/src/block.rs` sums each verified non-coinbase miner fee and obtains any deferred contribution from the funding-stream map. The pinned regtest configuration activates NU5, NU6, NU7, and SWAP at height 1. `zebra-chain/src/parameters/network/testnet.rs::new_regtest` empties both funding-stream sets, so at candidate height 205 there were no required transparent funding outputs and no deferred contribution. The block template confirmed a single miner output and `coinbasetxn.fee = 0`.

The prior failure's narrow source was `src/components/transactions.rs::template_into_proposal`: it copied the template coinbase after adding a non-template transaction. The template had 625,000,000 zatoshis for the miner, while the new swap transaction carried a 5,000-zatoshi fee. ZIP-236 therefore required **625,005,000 zatoshis** in the coinbase output. Adding 5,000 to an arbitrary output would have been wrong if the template already contained mempool fees or funding streams.

The correction is confined to the non-frozen tx-tool's `src/components/transactions.rs`. `FeePayingTransaction` carries a fee derived from the finalized transaction and its transparent prevouts; `mine_with_fees` independently checks it before submission. The proposal sums all supplied fees with checked arithmetic, subtracts the fees already included in the template coinbase, and applies the resulting difference only to the output matching the miner script. It requires exactly one such output and preserves all other outputs and any deferred treatment. The modified unsigned coinbase is refrozen so its txid changes. The builder then recomputes the transaction Merkle root for every proposal, the authorizing-data root, the block-commitments hash, and the block header hash before serialization in `BlockProposal::write`. Signed transaction bytes are not patched. The zero-fee case retains the original template coinbase. An invalid template fee, payout overflow, fee mismatch, missing prevout, missing miner output, or stale Merkle root fails before submission. The local SWAP-height guard checks the pinned regtest library assumption; an independently configured node still needs its activation settings verified, as done for this experiment.

No consensus rule, frozen Zebra or Orchard source, lineage relation, proof key, parameter file, Phase 3 verifier, dependency manifest, or remote was changed.

## Regtest evidence

A fresh disposable pinned Zebra node was used on loopback port 18239. An initial local command stopped before transaction submission because its disposable SQLite table was absent; a second attempt stopped after empty setup blocks because the existing proof-parameter directory was not supplied. After initializing that table and pointing `XDG_DATA_HOME` at the existing read-only parameters, the recorded run accepted setup blocks, issuance, and the zero-fee two-ZSA control. Those setup interruptions did not submit a positive-fee block.

The zero-fee control transaction `3676229c5c3ebde01e786f71b7b0b8d48209349d25704cd40cd05764c6725795` was accepted at height 204. `submitblock` returned `{"result":null,"id":"zcash-tx-tool"}`. Independent `getblock 204` returned RPC-display block hash `9234824c0be56a4fc0ae69cbf07bda8c8997700356e3a50219806473591a16df` and listed that transaction. The tx-tool's in-memory block-hash display used the opposite byte order (`df161a59...823492`); the RPC value is used for chain reporting. The control's accepted asset effects were X balances (Party A 990, Party B 9, matcher 1) and Y balances (Party A 5, Party B 14, matcher 1). Party B's shielded native balance was 625,000,000 zatoshis and the matcher's was zero.

The positive candidate was the **only** positive-fee submission. Its signed transaction hash was `5d03b30b1eedd53ea390dbb8079e1762df816dec4e08f6c06def8e480390cbed`; its candidate block hash was `64bc2e9929b0fcc4dcb1fedf9135e09444817444fe34f93fab4404c6c447d9d7` at height 205. The transaction had three Orchard Action Groups and zero aggregate native Orchard value balance. Its mature height-2 transparent funding output was `52d16b3f37b8e0a2cc1cf889b5ac7f8be6de18aef724fd601afbef1d9843cf6e:0`, value 625,000,000 zatoshis, with the expected miner script and serialized internal-order outpoint. Height 205 is 203 blocks after height 2, exceeding the 100-block maturity threshold. The signed transaction parsed back to the same txid. Its one transparent change output was 624,995,000 zatoshis; checked subtraction yielded the **candidate fee of 5,000 zatoshis**. The candidate coinbase paid 625,005,000 zatoshis to the miner, with no funding-stream or deferred outputs required under this regtest configuration. The signed swap bytes were unchanged during block assembly; the candidate transaction was 34,474 bytes.

The exact RPC response was `{"result":"rejected","id":"zcash-tx-tool"}`. Zebra's log identified `CommitSemanticallyVerifiedError(UnshieldedTransparentCoinbaseSpend)` for that block hash and height. The pinned source `zebra-state/src/service/check/utxo.rs::transparent_coinbase_spend` states that a transaction spending a transparent coinbase output must have **no transparent outputs**; maturity alone is insufficient. This is a later contextual rule than the Phase 3.5B fee mismatch, and the rejection is not evidence that the 5,000-zatoshi network fee was paid on chain. The command's nonzero exit was its `.expect` panic after the RPC rejection; the node stayed healthy.

The independent post-submission query returned best height **204** and best hash `9234824c0be56a4fc0ae69cbf07bda8c8997700356e3a50219806473591a16df`. `getblock 205` returned code `-8`, `block height not in best chain`; `getrawtransaction` for the candidate hash returned `Transaction not found`. **Accepted positive-swap effects: none.** The builder had calculated, but consensus did not accept, X balances (Party A 980, Party B 18, matcher 2), Y balances (Party A 10, Party B 8, matcher 2), shielded native balances (Party B 624,999,995, matcher 5), transparent change 624,995,000, a 5,000-zatoshi miner fee, and a 625,005,000-zatoshi candidate miner payout. The accepted chain remained at the zero-fee control balances above.

Diagnostic logs were retained locally at `/private/tmp/zwa35c-positive.log` and `/private/tmp/zwa35c-zebra.log`; the temporary positive-swap probe was removed from the isolated source before committing. Its probe-only transaction construction changes are not part of the product or tx-tool commit.

## Owner review gate and remaining blockers

The fee-accounting change is reviewable, but the mission's positive acceptance criterion was **not met**. The next experiment would need a network-fee funding source compatible with Zebra's coinbase-spend restriction and a fresh, owner-reviewed, single submission. That work is outside this phase; no ZSA-for-ZEC purchase or checkout flow should proceed from this result. The explicit-fee proposal API requires a correct prevout lookup and signed transaction value balance; transactions with unavailable prevouts fail closed. The pinned image and source commit were checked separately; the image tag alone is not a source-provenance claim. No architecture or dependency change was made. Security impact is confined to checking fee claims and coinbase arithmetic before submission; consensus validation remains authoritative.
