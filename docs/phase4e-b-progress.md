# Phase 4E-B progress — private funded offers and pre-approval reservations

**Status: PARTIAL.** The complete persistent order lifecycle and authenticated browser API are not implemented. This module is an internal, operator-controlled pre-approval ledger; its `QUOTE_READY` records do not confer proof authorization or permission to sign.

## Internal interface

`exchange/order_ledger.py` stores owner-only SQLite records under a private session root. `create_live_offer(root, container, port, seller_id, instrument_id, capacity, idempotency_key)` first checks the pinned chain manager's live anchor, then rebuilds the latest private buyer/seller portfolio from fresh independent wallet scans and accepted trade evidence. It rejects an absent/stale scan and limits an offer's capacity to the actual scanned seller inventory. `OrderLedger.request_purchase` reserves units with `BEGIN IMMEDIATE`; competing requests cannot both allocate the same capacity. Buyer-scoped idempotency keys make a retry return the original order, and a changed request using the same key fails. `attach_quote` checks the existing canonical Phase 4C.1 QuoteV1 digest, AssetBase, quantity, and exact next-block target. `close_before_approval` releases units only before signer approval begins. An append-only sequence records each order state change.

There is **no HTTP route** for these methods. A future service must authenticate the buyer/seller, check resource ownership, revalidate live chain and wallet inventory for every operation, and bind the accepted pricing snapshot before exposing a purchase action. Unit reservations are not note-level locks; a coordinator must still prevent simultaneous spends of the same Orchard note. The module deliberately has no `PROOFS_VERIFIED`, `BUYER_APPROVED`, `SUBMITTED`, or `RECEIPT_AVAILABLE` transition because actual verifier and signer events are not yet wired to it. Timeouts after any future approval must not be treated as consensus cancellation.

## Real private-root exercise

On the surviving Phase 4E-A chain at height 1,114, the adapter created three private offers from fresh seller wallet scans: gold capacity 93 units, Treasury-style capacity 95 units, and credit capacity 97 units. Their AssetBases match the three issued identities in `phase4e-a-report.md`. One buyer request for a gold unit was created and cancelled before authorization; its reservation returned to the offer. A separate one-unit gold request was given an actual pinned-coordinator QuoteV1 for 1,000 zatoshis, digest `acc0dc68bc573e71e72e076b3b1ec83455cf0186587b373ed9e0b98bdafa07c0`, target height 1,115. The order is **QUOTE_READY only**. Its payment is an operator-selected test amount, not a live gold/NAV/ZEC-converted price; no Groth16 proof, signer approval, transaction, or receipt was generated for it. The private database and quote files are under `/private/tmp/zwa4e-phase4e-b/exchange/` and are not committed.

## Validation and remaining work

The ledger tests exercise double-listing rejection, two concurrent purchase reservations, idempotent retry, changed-key replay rejection, mismatched or stale QuoteV1 rejection, buyer ownership on cancellation, reservation release, and ordered durable events. No dependency was added. The next integration must derive quote terms from a verified versioned pricing statement, enforce real authenticated actor identity, drive each post-quote state only from trusted proof/wallet/node events, and reconcile submission after crashes and reorgs. Until then, no offer in this ledger is `BUY_ENABLED` in the public catalog.
