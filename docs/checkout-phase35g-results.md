**COORDINATOR_READY_FOR_LOCAL_UI** for a **read-only UI and operator-run, disposable regtest checkout**. A new isolated run executed a 7-unit ZSA purchase for 10,000 zatoshis with independently signed buyer and seller Action Groups. The separate sponsor funded the 5,000-zatoshi network fee. A local Unix socket carried the signed groups directly to a single coordinator process; no signed-group envelope or assembled transaction file was written by the normal Phase 3.5G path. Pinned Zebra accepted the purchase at height 103. The API observed it at one confirmation, then observed K=3 depth after two empty blocks. The front end must not offer an actionable Buy button: there is still no human-facing wallet approval integration.

This remains the **legacy experimental ZIP 228 swap consensus pin**, separate from the Phase 3 rooted-lineage research baseline. The received note is not `NormalLineageStepV2` reachable. No production, mainnet, investor-eligibility or legal RWA ownership claim follows from this purchase.

## Mandatory authorization audit

- **Buyer SpendAuth:** Signs the buyer's Action Group commitment. That commitment covers every buyer action's nullifier, note commitment, ephemeral key, encrypted ciphertexts, value commitment and randomized validating key, plus the group's flags, anchor, expiry and burns. The buyer wallet proves and checks its own selected note inputs, recipient and net effects: 10,000 native zatoshis out, seven units of the exact custom asset in. The numerical group value balance is not itself part of its SpendAuth digest. Counterparty identity, other groups, network fee, transparent sponsor fields, branch ID and global transaction expiry are outside that signature.
- **Seller SpendAuth:** Covers the corresponding seller group fields, with own effects of seven custom-asset units out and 10,000 native zatoshis in to its own address. It has the same exclusions. Neither party's group signature cryptographically binds which other wallet's group will be matched, though valid own effects remain fixed.
- **Aggregate binding signature:** The coordinator computes it from both parties' disclosed binding-key shares plus its sponsor share. The signature digest covers the **ordered Action Group commitments and aggregate native value-balance number**; the validating key also enforces the aggregated value commitments, including per-asset conservation. It does not bind transparent sponsor inputs/outputs, fee semantics, branch ID or global transaction expiry. The sponsor's transparent `SIGHASH_ALL` signs the complete final transaction, but that sponsor signature belongs to the coordinator's disposable fee role, not either trading party.
- **Changed fee or sponsor input:** A malicious coordinator can construct another consensus-valid transaction with a different network fee or an extra sponsor input while reusing the parties' signed groups; Phase 3.5F proposal probes accepted both shapes. The Phase 3.5G normal coordinator locally requires exactly three groups, one exact mature sponsor outpoint, no transparent outputs, exact sponsor change and a recomputed 5,000-zatoshi fee. Those checks fail closed before submission, but they are **application policy**, not a consensus restriction on whoever holds a released group.
- **Recipient substitution:** Changing a signed group's recipient/ciphertext invalidates its SpendAuth or proof. Each signer independently checks the raw receiving address against its own wallet and derives exact own effects from the signed group before release. The coordinator validates both commitments and the serialized final transaction. A coordinator cannot redirect an existing signed group's output, but can pair it with a different balancing counterparty group.
- **Expiry and reuse:** Pinned Zebra enforces the final transaction's global expiry, but the coordinator chooses and sponsor-signs that field. A malicious coordinator retaining an already disclosed signed Action Group and binding share can place it in a **different** final transaction with a later global expiry, until its input nullifiers are spent. Group expiry `113` is signed but not enforced by this node. Local next-block approval, journal replay rules, `EXPIRED_LOCALLY`, a closed socket or a failed session do **not** cryptographically cancel a released group. No standing orders, reusable offline approvals or enforceable cancellation are claimed. Spending the original wallet input notes is the practical way to invalidate a disclosed group; that cancellation workflow is not implemented here.

The canonical `quoteDigest` is a domain-separated, fixed-width **off-chain review token**. It is not a consensus signature of the complete transaction. The original Phase 3.5F `terms_hash` was a BLAKE2b hash of JSON; the recorded Phase 3.5F sample is retroactively encoded as QuoteV1 for display and is clearly marked recorded. New signers and the new coordinator use QuoteV1's canonical digest.

## Components and transaction flow

1. **Independent wallet signer:** Each buyer/seller invocation uses its own mode-0700 home, mode-0600 seed and separate SQLite note database. The macOS sandbox profiles deny access to the other role homes. The signer rechecks chain identity, own balance/note selection, asset, quantity, price, own recipient, counterparty recipient, target height, approved quote digest, proof, SpendAuth and recovered own effects. `authorize-live` journals the note nullifiers before releasing the group, then sends one bounded envelope over a local Unix socket. It exposes no HTTP signing API or spending key.
2. **Checkout coordinator:** `prepare-sale` creates one fixed-price QuoteV1 and one public session-result file. `execute-live` receives one buyer and one seller envelope over the socket, rejects missing/duplicate roles, verifies group proofs, signatures, common anchor and distinct nullifiers, assembles with the one disclosed sponsor input, round-trips and fully verifies the serialized transaction, checks exact fee and global expiry, then submits and observes one purchase block. Only the public receipt remains in the session-result file. The socket pathname is removed on completion; signed groups and the assembled transaction are not written to files in this normal path. Rust memory is dropped at process exit, without a guaranteed zeroization claim. The older Phase 3.5F file-based `assemble`/`submit` commands remain for historical research and adversarial probes, not the normal Phase 3.5G flow.
3. **Read-only status API:** `checkout/api.py` reads exactly one bounded public session-result file and queries fixed Zebra RPC methods (`getblockchaininfo`, `getblock`) on loopback. Pinned Zebra reports regtest as RPC chain `test`, so the service pins the exact regtest genesis hash, SWAP next-block branch and height-1 activation as well. It does not invoke the coordinator, wallets or a general shell, and cannot access seeds, wallet DBs, signed groups or signer IPC secrets. Historical Phase 3.5F evidence has a separate literal route. Unknown origin/host, cross-site browser requests, bodies and mutating HTTP methods are rejected. There is no permissive CORS.

QuoteV1 contains the required asset, quantity, payment, role-specific receiving commitments, fee payer, network and matcher fees, buyer maximum debit, transaction expiry, ID and digest, plus the pinned SWAP branch, target height, group expiry and exact sponsor outpoint/input/change. The digest uses 32-byte BLAKE2b with personalization `ZWA35G_QUOTE_V1\0` over fixed-width little-endian fields. The receiver commitments are role-domain SHA-256 hashes of raw Orchard receivers. Exact schemas and the recorded example are in [checkout-ui-api-contract.md](checkout-ui-api-contract.md).

## Status and failure behavior

The API never reconstructs a transaction as accepted from a quote or a stale local file alone. It validates the exact session schema and digest, then rechecks the block hash, txid and confirmation count against the current node on every live read. Node outage returns HTTP 503 with `status: null`. A mismatch returns `INVALIDATED_BY_REORG`. On restart, a file marked `UNCERTAIN` stays unresolved rather than becoming accepted. Pre-submission failures are recorded as `FAILED`; local expiry is `EXPIRED_LOCALLY` and explicitly does not revoke disclosed groups. A missing receipt yields `RECEIPT_NOT_AVAILABLE`, and a corrupt result yields `INVALID_SESSION_RESULT`. Only one configured session file is served. Historical evidence is always `RECORDED_REGTEST_EVIDENCE`, never a dynamic purchase.

The normal CLI has no network listener and the HTTP interface has no state-changing route. The operator can still misuse the older research CLI or copy a signed group outside this flow; this is a test harness, not a production custody boundary. The demo approval hash was supplied by a script after the CLI review outputs. No person reviewed and clicked Approve in this run.

## Limits and next risks

Pinned Zebra does not enforce Action Group expiry; a retained signed group remains a bearer authorization until the input note is spent. The sponsor controls final transaction expiry and fee-bearing fields. The API's digest and local checks cannot eliminate that risk. Same-user macOS sandbox profiles are weaker than independent machines or hardware wallets. No human wallet UI, explicit note-spend cancellation, production wallet support, mainnet compatibility, legally authenticated RWA ownership, rooted-lineage proof of the received note or investor-eligibility decision exists. The separate Phase 3 rooted verifier must continue to report its own evidence independently.
